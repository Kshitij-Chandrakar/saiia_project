## Google-only reauthentication: evidence and decision

Current website login calls `signInWithOAuth({provider:'google', options:{redirectTo:...}})`. It does not request, receive or server-validate a Google `auth_time` proof bound to the deletion operation. The existing Supabase browser configuration does not explicitly select PKCE; this stage leaves ordinary login/callback behavior unchanged and makes no claim that all existing callbacks use PKCE.

Google's current [OIDC reference](https://developers.google.com/identity/openid-connect/reference) documents an optional signed `auth_time` claim requested through the claims parameter. This is a possible future proof source, **not proof that our current redirect returns it**. The same reference lists prompt values for no UI, consent and account selection; it does not establish a generally supported forced-fresh-login mechanism for this integration. A current token issuance time or successful chooser is insufficient. Supabase's [Google integration](https://supabase.com/docs/guides/auth/social-sign-in/auth-google) and the installed SDK do not supply an existing application contract that binds provider authentication time to our operation. Upstream [Google adapter source](https://github.com/supabase/auth/blob/master/internal/api/provider/google.go) is current reference code, not the unknown deployed Auth version or acceptance evidence.

Therefore **no new Google deletion redirect/callback was introduced**. Google-only accounts with an existing verified TOTP can use Stage 1B; those without one remain blocked. No password creation or mandatory authenticator enrollment was added. Refresh, OAuth AMR time, account choice and client time remain rejected as substitutes. Existing operation/session proof binding, explicit final confirmation, account-switch/unmount and cancellation behavior remain tested. There is no newly implemented OAuth return that could auto-delete; provider cancellation/success on such a flow is not claimed tested.

## Supported integration package and hook security

The generator omits only the pinned Stage 1 managed-Auth guard segment, preserving unrelated storage/content/email/billing safeguards, then includes Stage 1B and the new Stage 1C public-object changes. It emits a single transaction. The old migrations remain unchanged as historical source.

**Do not run the repository's historical C15 migrations and then this package together.** For a later fresh isolated rehearsal, use the required pre-C15 schema/dependencies and this package instead of those C15 files. Existing databases where historical C15 migrations were actually applied need a separately reviewed upgrade path; this package is not that repair migration. Nothing was remotely applied. Default SQL configuration stays disabled; there are no real keys or sample credentials in the artifact.

Supported hooks are `public.privacy_auth_before_create(jsonb)` and `public.privacy_auth_token(jsonb)`. Only `supabase_auth_admin` receives EXECUTE; application/public/service/executor roles cannot call them. Direct session caller authority is also checked; an unverified SET ROLE/gateway arrangement is not silently accepted. Target Auth caller identity must be confirmed in later integration. Legacy helper EXECUTE is removed from Auth and helpers are not configured as hook entry points.

Hook wrappers bound JSON size to 32KiB, validate object/UUID/required claim shape and subject consistency, preserve valid claims and delegate the existing keyed suppression logic. Failures are opaque; missing suppression key yields safe unavailable/503. No public lookup endpoint or HTTP hook was added, so there is no new webhook-signature secret. Trusted migration-owned SECURITY DEFINER functions have fixed search paths; untrusted CREATE on public is revoked. `supabase_auth_admin` gains no direct SELECT on suppression/crypto tables. Function-owner privileges and existing hooks must be reviewed before real deployment; never overwrite an existing security hook without composition.

Each wrapper has a 750ms lock timeout. Supabase documents a two-second PostgreSQL-hook execution limit in its [hook contract](https://supabase.com/docs/guides/auth/auth-hooks); native tests do not claim to run the actual Auth-enforced timeout. [Configuration documentation](https://supabase.com/docs/guides/self-hosting/self-hosted-auth-hooks) describes the `pg-functions://postgres/<schema>/<function>` URI and SQL-hook role. The [before-create contract](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook) and [token-hook contract](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook) remain the integration authorities.

Suppression remains versioned server-keyed HMAC, pseudonymous data, ASCII trim/lower only, with no Gmail dot/plus equivalence. The encryption key ring described next is separate from these matching keys. Existing missing-key denial, key-version retention and restore-suppression requirements remain unchanged. No backup/provider expiry promise is added.

## Revocation credential lifecycle

1. The existing backend re-verifies the bearer/subject and recent confirmation proof. At final confirmation it encrypts **only that verified access JWT**, never a refresh token, password or Google credential. AES-256-GCM uses a random 96-bit nonce and authenticated purpose/account/request/key-version/expiry context. Expiry is the earlier of JWT expiry and five minutes; acceptance requires enough remaining lifetime to enqueue safely.
2. The new SQL wrapper locks the account and atomically commits accepted request, existing barrier/audit/tasks/suppression and ciphertext in `privacy_revocation_credentials`. Failure rolls all of that back. The required protocol function prevents a new backend from silently using old SQL that omits this requirement. Accepted replay never extends or replenishes the credential, even when encryption keys are missing; status remains narrowly scoped.
3. Task metadata/audit/status contains no plaintext token or ciphertext. The separate FORCE-RLS credential table has no direct app/service/executor SELECT; its private RPC returns ciphertext only to the existing executor with the exact live request/account/lease. Decryption authenticates the account/request and the worker again verifies the signed JWT subject/role before any HTTP call.
4. Browser acceptance clears attributable local SDK storage, stops refresh and replaces the whole document with the status page. **It no longer calls remote local-scope SDK logout first**, which could invalidate the queued capability's Auth session. No full product access remains: existing HTTP/gRPC/RLS/content barriers are already authoritative. Closing the browser does not remove the server-side encrypted capability.
5. The opt-in worker uses the supported HTTPS `/auth/v1/logout?scope=global` route with the target JWT and configured public API key. No administrative user-ID-only API was invented and no new service-role credential is needed. The [admin SDK reference](https://supabase.com/docs/reference/javascript/auth-admin-signout) and installed source require a JWT; [global signout documentation](https://supabase.com/docs/guides/auth/signout) distinguishes refresh-session revocation from access-token expiry.
6. Existing 30-second leases, five-attempt cap, delayed retries and stale-worker rejection are reused. HTTP has 3-second connect/10-second read inactivity timeouts, no redirects, no response-body reading, and closes the response. These are socket timeouts, **not a claim of an absolute wall-clock guarantee**; lease fencing rejects late completion. Only confirmed HTTP 204 acknowledges success. 401/403, expiry/key failure or wrong account cannot prove global success. Missing credential blocks follow-up honestly; transient/timeout outcomes retry while usable.
7. Ciphertext is removed on acknowledged success/terminal blocked state or expiry. Expiry is checked on every worker RPC and by the existing recovery loop independently of key availability/provider-worker configuration, while restriction enforcement is required. An outage can delay physical row removal until recovery; deadline checks make it unusable meanwhile. No exact physical-backup-erasure promise is made. Required key/config changes need worker restart; pending requests remain restricted if composition is unavailable.
8. If Auth succeeds but the process dies before acknowledgment, retry may see a rejected session credential. That rejection remains **blocked/unknown**, not inferred success. The supported API still depends on a valid session credential; another logout/ban/expiry can make completion impossible. Actual target-version behavior needs Auth acceptance. Never clear billing identity/provider linkage or mark personal cleanup/account erasure complete merely because session revocation succeeded.

Python cannot guarantee zeroization of immutable token strings or keys in process memory. No plaintext persistence/logging is introduced; request headers/crypto state remain trusted server-memory material. Response/body/error payloads are not recorded. DB backups can contain ciphertext; encryption keys must not be stored with those backups. Neither encryption nor access-token expiry proves all backup bytes were erased.
