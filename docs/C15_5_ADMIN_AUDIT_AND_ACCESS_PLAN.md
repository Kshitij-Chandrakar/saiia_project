## One authoritative membership model and migration

Propose unique `admin_memberships.user_id`, one authoritative row per subject, role/status/revision plus safe invite/revocation history. Exactly one active membership is loaded server-side per request; invited/suspended/revoked grants nothing. Mutation rechecks membership/revision under transaction locks. Revocation, not row deletion, preserves history. Account deletion transitions membership to revoked/pseudonymized-revoked under C15; Auth FK treatment must be reviewed, not cascade away evidence.

Existing `subscription_admin_permissions` is the starting authority. Migrate through a separately approved, additive compatibility layer:

1. Inventory subject/permission/revision/active state without exposing identities in reports. Dry-run mapping and collision checks; no inferred broad role.
2. Record explicit approved role assignment only when owner authorizes it. Legacy principals retain **only** subscriptions.manage, billing.read and/or billing.manage already held. A restricted legacy capability profile may exist under the one membership authority during transition; it is not a second role registry or union fallback. Role assignment that expands rights requires a separate approval/reason/audit/step-up.
3. Move all catalog/billing/general checks to one authority and compatible permission resolver in an atomic cutover; preserve legacy API permission strings and revision-conflict behavior. Compatibility output derives from new authority only. Never OR old active rows with new membership grants.
4. Freeze legacy maintenance writes, compare old/new effective rights, ensure suspended/revoked denies every path including queued execution. Retain legacy rows read-only as audit evidence or expose compatibility views. No dual active sources.
5. Rollback only through a reviewed snapshot/revision procedure that carries every intervening revocation forward; do not reactivate old grants. Default off while rights differ. No real backfill/provisioning occurs under this audit.

First-owner provisioning is a separately reviewed restricted maintenance procedure with independently verified subject, reason, step-up/recovery controls and audit. No public bootstrap or frontend secret. Routine invitations cannot replace it. First owner does not authorize an unapproved support rollout.

## Exact access matrix conventions

This is the proposed implementation contract derived from the roadmap, **not effective current grants**. O=owner, S=super_admin, H=support_admin, B=billing_admin, P=privacy_admin, A=security_auditor, R=readonly_admin. **Every role not listed in a row is denied**; normal users are denied all admin routes. “Blocked” overrides role eligibility until the stated decision resolves. All future rows are F (missing runtime/proposed), unless C (current narrow foundation).

Route abbreviations: `U=/api/admin/users/{user_id}`, `M=/api/admin/admins/{admin_user_id}`, `N=U/support-notes/{note_id}`, `T=/api/admin/sessions/{session_id}`. IDs are backend-resolved, ownership/target bound, never arbitrary user DTO reuse. Route spelling is a candidate compatible contract, not a mandate to duplicate equivalent existing catalog/billing APIs.

Controls: **L** verified identity + fresh active membership + permission/projection/target check + no-store; privileged reads audited before response. **W** L + bounded non-sensitive reason + explicit target/action confirmation + transaction/revision check + atomic success audit; failed/denied attempts separately safely logged. **H** W + recent verified MFA/step-up (proposed <=5min); high-risk read/use uses L + reason + step-up/confirmation + committed access audit. No implicit second-person approval unless row says it; absence of a roadmap approval rule is stated, not invented. Owner never bypasses any control.

## Plain-language role boundaries

- **owner:** manages admins, ownership and highest-risk settings; can perform the authorized support/billing/privacy operations. Cannot bypass reauth, confirmation, audit, last-owner safety, provider truth, C15 retention or break-glass approval by someone else. Cannot erase audit history through the console.
- **super_admin:** manages non-owner admins and broad support/billing/privacy operations. Cannot transfer/create/remove owner through generic routes, edit plans under the literal roadmap permission list, override payment state, or read raw content by default. Raw eligibility remains unresolved.
- **support_admin:** sees contact and safe profile/resume/session status, handles support locks/holds, initiates password resets, retries extraction/indexing, and writes internal_support notes. Cannot change security/billing/deletion state, force logout under the current matrix, inspect billing, execute privacy operations or read raw content by default.
- **billing_admin:** sees necessary billing/usage and can request eligible reconciliation/notification retry, reasoned usage adjustment and billing restriction changes. Writes billing_review notes. Cannot set paid success, change immutable terms, access resumes/transcripts, manage admins or execute deletion.
- **privacy_admin:** sees privacy requests and limited resource metadata, triggers exports/reviews/approved deletion and manages privacy_review notes. Cannot skip confirmation or use ordinary user endpoints as another user. Raw approval eligibility does not imply raw read permission; no default content access.
- **security_auditor:** reads audit-safe security/user/system metadata and note metadata, recommends action. Cannot change accounts/admins/usage, create notes or retrieve raw content. Email is hidden absent separately justified investigation.
- **readonly_admin:** sees operational aggregates/high-level status only. No default email, individual payment details, note bodies, privacy cases or raw content, and no mutations.

## Required transaction and lifecycle safeguards

**Status transitions:** implement exact allowed edges from the matrix, not unrestricted PATCH. The roadmap scalar “any → billing_restricted/disabled_by_security/pending_deletion” conflicts with safe concurrent restrictions. Recommend independent restriction causes with effective precedence deleted/pending_deletion > security > user/support hold > billing > active. Clearing billing must never clear security/deletion; terminal deleted cannot restore through status routes. Pending deletion needs approved review; delete confirmation enters deletion workflow, and final deleted semantics follow C15 completion rather than merely queuing work. This interpretation needs explicit signoff, not silent schema change. Native tests exercise concurrent independent holds/releases and stale revisions.

**Membership/ownership:** unique user_id and row revision; transactional role/status changes and locks over the owner invariant prevent concurrent removals leaving zero active owners. Generic role/suspend/delete rejects owner mutations; transfer route alone atomically changes ownership, verifies eligible active authenticated target, requires MFA/reason and commits audit. Failure leaves all roles unchanged. A revoked row is not physically deleted. Owner signup/invite contradiction remains blocked.

**Invite acceptance:** store hashed token only. In one transaction lock/validate invite, verified email match, accepted_at null, revoked_at null, expires_at > server now, actor/role eligibility; create/activate the single authoritative membership, set accepted_at and append audit. Concurrent acceptance yields one membership/one success; replay fails. Reinviting suspended/revoked members must not silently restore access outside approved rules. Token/email content is not audit metadata.

**Break-glass:** disabled pending raw eligibility/data-type decisions. Later permission plus grant both required. Header `X-SAIIA-Break-Glass-Grant` is sensitive and never enters URL/history/route params/logs/traces/error reports. Store hash/safe reference, bind authenticated consumer, target_user_id, resource ID/type, data type, purpose, separate eligible approver, expiry and unused state. Atomic compare-and-consume/access audit; two parallel uses cannot both succeed. No self-approval, owner exception or reusable signed object link. Stream the minimal approved object after committed grant/audit; if delivery fails, grant stays used and a new request is required. No grant for screenshots/audio/notes/chat/other types without separate explicit policy. No raw payload in grant/audit tables.

**Deletion review:** requested/approved/denied/expired/consumed/cancelled with every transition audited. Execution atomically checks approver policy, actor, target, scope/policy version, expiry and unused state; consumes approved request with deletion barrier/outbox and audit. External erasure occurs asynchronously, so consumption means exactly-once acceptance, not proof of physical completion. Recovery continues the same accepted request. Proposed separate approval endpoint must use delete_review for approval and delete_confirm for execution after the conflict is settled. A separate approver for deletion is recommended but not yet defined by the roadmap; do not claim it already approved.

**Audit:** normal users/admins cannot UPDATE/DELETE/TRUNCATE. Mutations and success audit commit together; sensitive reads require committed access evidence before data return. Safe denial/failure events must survive rollback via a bounded separate path without copying private payload. Audit unavailability fails closed for privileged data/action. Corrections append superseding records. Exceptional retention maintenance has a separate narrowly privileged identity, documented purpose and independently retained audit; no UI erase and no service-role silent mutation. This must extend/reconcile catalog/billing histories, not erase them.

**Notes:** enforce permission plus visibility, target and author identity server-side. Body cap proposed 2,000 characters; sensitive-content prohibition is established, numeric cap is a recommendation. Validators plus staff guidance cannot guarantee automated detection of all pasted private content; retain review/redaction/escalation. Notes store retention class/audit link. Normal user RLS and ordinary routes deny bodies. User export omits raw notes; any required metadata exception must be justified, redacted and scoped. Privacy role's generic delete_review cannot silently grant access to billing/internal_support bodies.

**Flags/credentials:** catalog entries specify key/type/allowed range/protected state/permission/step-up/reason. Unknown key/type/range and protected mutation reject. No secrets, arbitrary SQL, environment variable editor or payment-state switch. User-linked admin records include memberships, invites, audit, notes, break-glass and deletion-review records; user deletion follows C15 for those, never changes global flags/nonpersonal catalog history.

## Proposed information architecture and workflows

Use the existing website typography, surfaces, forms, responsive layout and catalog review interactions when implementation begins. No assets or UI were built during this audit.

- `/admin`: self permissions, operational health and allowed work queues; metadata-first, no default candidate content. Explicit loading/unavailable/not-admin/suspended/denied states; no fake zero data.
- Users: bounded lookup, safe role projection, resource status counts, permitted actions. Detail tabs only where authorized: overview/resources, sessions, billing/usage, privacy and notes. A role cannot learn hidden data through counts, search errors or disabled-control labels.
- Catalog/Billing: retain existing versioned catalog and narrow billing pages, link from authorized navigation; inspect → state-bound review → confirm → queued/unknown/result. No “success” for merely queued provider work.
- Privacy: subject request metadata, policy version/scope/retained exceptions, review/approval/step-up/confirmation, task progress and failures. Staff trigger delivers export to data subject; not staff download.
- Membership/Invites: unique member state, role/revision, explicit reason/confirmation, invite expiry/revocation and owner transfer. Last-owner warning mirrors backend enforcement.
- Notes: visibility clearly labeled, allowed body only; metadata for auditors, redaction/review workflow, content prohibition and retention status.
- Audit/System: append-only filtered safe event views; health/config allowlist. Break-glass queue separate from user detail; grant never in URL or persistent browser state.
