# C15 legacy immutable-record retirement proposal

31 October 2026, Asia/Calcutta. **Review-ready design, not an executable migration or authorization to retire history.** Source: local `work/c15-stage1`, baseline `682bd57520dd49ad16ba13c65104aa9deda4fffa` plus preserved uncommitted C15 implementation. Approved owner direction: bounded immutable lifetime, with separate restricted retirement. No existing history was rewritten, retired, copied to a payload-bearing archive or made mutable. C15.5/Razorpay remain paused.

## Recommendation

Use **closed, account-owned retention units and fixed, class-specific retirement procedures**, with a dedicated maintenance identity and guards that preserve immutability throughout the approved lifetime. Introduce minimal versioned envelopes and separately erasable private payloads for new writes first. Keep legacy rows blocked until their ownership, clock, dependency closure and reader compatibility are proved. Do not force all immutable records into the usage/security clocks.

This is the smallest compatible design because current replay/reconciliation readers depend on accepted row bytes and current FK graphs cross retention classes. Time partition drops cannot safely retire individual accounts in those mixed/shared partitions. Encryption-key destruction alone cannot erase plaintext UUIDs, copied JSON, FK edges or unencrypted history. A payload-bearing archive is another retained copy, not erasure.

## Retention unit and eligibility

Proposed additive metadata (names illustrative, not SQL prepared for execution):

- `retirement_unit`: opaque ID, schema/classifier version, exactly one proven owner or explicit shared class, accepted privacy-request reference, clock provenance, approved category, eligibility time, revision, sealed state, bounded retry/lease/fence, exception/hold references. Keep this pseudonymous metadata restricted.
- Fixed member relations per supported class enumerate exact row primary keys and dependency versions. No caller-supplied table, predicate, field, SQL or object prefix. No unit may span unrelated accounts. A shared row never becomes a customer unit member merely because one account references it.
- `retirement_hold`: approved purpose and authority, minimal field scope, accountable reviewer, next review time and release condition. Overdue review fails closed and escalates; it never silently authorizes deletion or silently extends a policy forever. Billing unresolved cases retain their approved seven-day review cadence. Other hold cadences require a justified decision rather than borrowing seven days.
- `retirement_run`: unit/revision, expected count/type counts, classifier/guard version, lease/fence, outcome category and non-content attestation. Durable checkpoints contain no record payload, raw email, token or filename. Any subject-linked manifest/replay marker has its own justified horizon; unlinking a UUID is not anonymization.

Eligibility is the conjunction of approved clock, complete ownership classification, expiry of **each** member's justified lifetime, closed writers/replay windows, no active holds/leases, compatible readers and no surviving dependent row requiring the member. Mixed 90/180-day units are split where possible. If inseparable, all purposes must be explicitly justified and the latest applicable approved deadline must have elapsed; this is not approval to assign 180 days to arbitrary usage or financial records. Financial/shared/no-clock units remain blocked.

## Exact maintenance capability and transaction

Proposed `privacy_retire_usage_unit(unit_id, expected_revision)` and, separately, `privacy_retire_security_unit(unit_id, expected_revision)` accept only opaque IDs and revisions. A NOLOGIN function-owner principal owns tightly scoped fixed SQL; a separately provisioned maintenance executor gets EXECUTE on only the reviewed procedure. Neither principal is an application/admin/service-role membership. Revoke PUBLIC/anon/authenticated/service-role/catalog/billing/ordinary worker access; test role inheritance, SET ROLE and direct DML denial. Superuser/operator control is outside application authorization and must remain separately controlled.

Existing unconditional guards currently make retirement impossible. **Do not change the shared `catalog_reject_mutation` function.** A separately authorized migration would attach dedicated guards to the exact approved legacy tables under one transactional DDL lock. Guards continue to reject every UPDATE and TRUNCATE, and every ordinary DELETE. A retirement DELETE is allowed only inside the fixed procedure's verified maintenance session/owner context, with a locked eligible unit/revision and internal transaction-bound execution permit in a restricted table. A forged GUC, role name, client nonce or unit ID alone grants nothing. There is no unguarded application-visible interval, disabled trigger, generic DELETE grant or routine accepting arbitrary SQL. This guard redesign requires security review and explicit rollout authorization; it is **not implemented here**.

Within a retirement transaction:

1. Lock unit, account/restriction identity, relevant binding/operation/period parents and exact members in documented stable order. Recheck server clock, class/version, membership revision, holds and lease/fence after locking; seal writers first.
2. Verify counts and all incoming FKs, including member-to-member RESTRICT edges and JSON semantic dependencies. Unknown dependency aborts, never cascade-delete a parent to force progress.
3. Create the private transaction-bound permit; delete fixed children before parents. Financial evidence/shared catalog, suppression and restoration markers are excluded. Reconcile retained totals/replay denial before removing old event evidence. No live-account aggregate is silently rewritten.
4. Verify exact expected member absence and unchanged nonmembers, ledger invariants and exception records. Write a payload-free attestation and terminal unit checkpoint in the same transaction; consume permit. No uncertain partial DB commit can be reported as success.

Crash before commit rolls back. Crash after commit is recovered by unit/revision terminal state, not repeating side effects. Stale fences and semantic conflict reject. External object retirement, if ever added, requires existing durable task/absence verification semantics and a separate approved scope; it is not part of these legacy procedures. An archived raw payload is prohibited as a rollback technique.

## Replay and compatibility

Before sealing any unit, all writers must enforce account restriction/generation fences and durable retired-key denial. Remove product access before erasure. Financial late events may append minimum verified facts through the existing signed/deduplicated authority, but cannot recreate a Free/paid binding, profile, raw content or ordinary marketing. Retired event/request identities need restricted non-content denial markers for the required callback/recovery horizon; no guessed expiry. A lookup of a retired reply returns a deterministic retired outcome, never a fresh operation.

For new writes, introduce versioned minimal envelopes and separately erasable private result/credential sidecars. Dual-version readers must return existing immutable results unchanged while they remain retained; no SELECT-* fallback, fallback to recreating an operation or rewriting an accepted receipt. Quantitative accounting stays provably reconcilable. Old row versions with incomplete field classification remain blocked. Do not copy historical content to a new table and claim the old payload erased.

## Preparation, dry run and separately authorized rollout

1. Add restricted unit/classification/hold/run storage and read-only eligibility routines; default execution disabled, no LOGIN/grants/key creation. Schema-drift tests must require every new table/field/consumer to declare treatment. No history backfill yet.
2. Implement forward envelope/sidecar writers and dual-version readers in small separate review slices, preserving accepted billing/payment/email evidence. Verify canonical response/replay equivalence, totals and denial after deletion.
3. Produce counts only by class, clock coverage, blocker/FK type, ownership certainty, live lease/hold and retained financial/shared dependencies. Operator detail is separately permission-checked; reports must not dump payloads, UUID lists or emails. Missing clocks/ownership go to a blocked queue, never an inferred expiry/backfill date.
4. Seek separate authorization for bounded metadata backfill, dedicated trigger/procedure installation and synthetic staging acceptance. Compare before/after hashes of existing immutable bytes **internally** where needed; do not publish hashes as anonymous data. Re-run all privilege/consumer/FK/race tests.
5. Only after an approved complete eligibility report and external restore-marker integration: separately authorize limited retirement batches, with stop limits and payload-free attestation. No execution is authorized by this proposal.

Disabling future execution revokes/halts the maintenance capability and preserves deny markers/attestations. It does **not** restore irreversibly retired data. A restored old backup must replay the retirement/deletion journal before access; blindly restoring rows is resurrection, not rollback.

## Acceptance and decisions

Required deterministic later tests: exact class/clock boundaries, ordinary-role/direct DML/TRUNCATE/GUC denial, mixed and shared-unit protection, missing clocks, hold review, FK dependency closure, concurrent hold/writer/role changes, same-unit races, stale leases, crash/uncertain commit, late callbacks/replay and deleted-data restore. Compare retained billing totals/provider linkage, unaffected accounts and global catalog/flags. Use disposable synthetic tables first; no retirement prototype against existing legacy tables was run here.

The owner has already chosen bounded immutability. **No repetition of that decision is needed.** Remaining decisions are narrower: statutory/contractual financial scope/lifetime (external/legal); explicit classifications for mixed legacy payloads; and approval of the exact guard/procedure migration after review. Engineering/security must supply dependency-complete eligibility and deployment identity controls before requesting execution approval. See [durable restore implementation](C15_RESTORE_CHECKPOINT_LOCAL_IMPLEMENTATION.md) for the independent implemented deliverable and its deployment limits.
