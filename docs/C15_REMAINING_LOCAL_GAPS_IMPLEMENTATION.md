## Exact treatment and integrity limits

The executable export allowlist remains `privacy_registry.py::CONTENT/SAFE_METADATA`, with frozen field inventory in `backend/app/privacy_fields.json`. Added user-visible fields include resume status/confirmation, job location/employment/file metadata, settings dictionaries and onboarding state. Original-file export, archive safety, own-account snapshotting and bounded archive limits remain unchanged. The 1 GiB/10,000-entry limits are configurable engineering defaults; exceeding them fails explicitly, never truncates. Numeric embeddings, credentials, suppression identifiers, internal prompts/security/retry payloads and support notes remain excluded.

Settings dictionaries have no existing application producer establishing a narrower semantic schema. They are classified as user settings, bounded to 64 KiB/depth 8, with finite JSON values and credential-key/value rejection. Unknown job metadata keys block export. This does not authorize deleting unowned local JSON files. New fields require intentional reviewed classification; the request path never regenerates the manifest.

New minimized records contain only `account_id`, source UUID/kind, category, enum-like event/outcome, optional quantity/event time, confirmation/deadline and worker lease fields. UUIDs and keyed identifiers remain **pseudonymous personal data**. They are not anonymous. Financial evidence, permanent suppression, lifecycle/restore markers and external copies retain separate treatment. Unapproved temporary/orphan clocks remain disabled. The new retirement role cannot choose an arbitrary table, account, target or clock and has no ordinary application grants.

## Restore contract and limits

The native rehearsal stops only its disposable cluster, copies its cold data directory, restarts the source, accepts synthetic deletion and publishes evidence **outside** the snapshot, then starts the clone on another loopback port. Replay blocks restored product use/profile writes, preserves suppression and drives fake-Storage personal cleanup. Separate tests cover session scope and missing/corrupt/stale checkpoint/key failures. No hosted backup, Auth engine, actual Storage object service or customer data participates.

The journal keyring and trusted latest checkpoint must live outside every restore set. Publishing uses a transactional outbox and serialized local publisher; **production scheduling, independently durable checkpoint publication, atomic deployment cutover and proof that no accepted decision is missing remain activation blockers**. A stale-but-trusted checkpoint could omit newer decisions; production must freeze/compare the live outbox and independently witnessed checkpoint before opening traffic. No backup-erasure deadline is promised. Session-linked email or immutable FK failures quarantine restore instead of serving incompletely erased data.
