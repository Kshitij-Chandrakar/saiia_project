## Persistent authority and trust boundaries

The **encrypted journal** contains accepted account/session erasure decisions, matching-key fingerprints and scope evidence. It remains separate from database/object snapshots. The **local checkpoint store** persists a versioned HMAC-authenticated record: environment UUID, dataset UUID, monotonic sequence, encrypted-journal head, sealed source head, restore-generation UUID, combined snapshot-manifest identity and readiness acknowledgement. No raw email, token, object path or content enters checkpoint health diagnostics.

An independently located **witness** contains the current authenticated checkpoint. Reading requires mirror/witness byte equality, valid HMAC/version and exact environment/dataset binding. Wrong generation/snapshot, missing/truncated journal, head mismatch or rollback of the dataset plus local checkpoint fails closed. The expected current head is obtained from the protected current witness, never from a restored DB row or a browser-supplied hash.

The isolated SQLite implementation uses `BEGIN IMMEDIATE`, attached rollback-journal databases and `synchronous=FULL` for local atomic mirror/witness updates. Journal append fsync occurs first. If append/DB outbox acknowledgement succeeds but checkpoint commit fails, recovery accepts only a journal extension containing the trusted prefix and decision IDs still present in the live outbox; it reconstructs/rechecks exact decisions through the existing gate before acknowledging. Unknown/conflicting tails remain blocked. Duplicate publishers serialize and return the same sequence without duplicate decisions.

This local transaction choice follows SQLite's documented [attached-database atomicity conditions](https://sqlite.org/lang_attach.html): file-backed main database and rollback journaling, rather than WAL. No claim of tested physical power-loss durability or cross-service PostgreSQL/SQLite atomic commit is made. Source quarantine commits before the source seal is acknowledged; the deployment fence remains required throughout cutover.

**Freshness has a trust root.** The witness and authentication/journal keys must be protected outside every restored input and supplied by an operator control plane. A signature alone does not prove recency. Rolling back *all* trusted witness/key/control-plane state is not detectable by a local signature; this implementation makes no such claim. A local second file is a rollback-test boundary, **not production independent durability**. Production must supply a conditional, strongly consistent durable checkpoint/witness service with access separation and tested failure semantics; no cloud service was invented or configured here.

Sequence advances when journal coverage changes, source cutover is sealed or an operator CAS authorizes a new generation. Readiness acknowledgement for the same head is idempotent. New decisions invalidate the seal/readiness until published and sealed again. Every accepted request and session/history scope must have a matching outbox record; every current outbox entry must acknowledge the witnessed head. Missing historical capture is a blocker, not evidence of zero decisions.

## Source cutover and reconciliation

1. **Before restore**, the deployment control plane must stop/fence old-generation ingress, queues and provider callbacks that could accept new decisions. `seal_source()` runs on the **live source**, locks deletion requests/content jobs, publishes complete accepted outbox coverage, commits source quarantine, and records a sealed head plus target generation/snapshot identity. Never run source sealing on an old restored copy to manufacture completeness.
2. `reconcile()` commits target quarantine before reading evidence. It requires a witnessed sealed head and matching environment/dataset/generation/snapshot. No ordinary account/admin route can set readiness or invoke coordination.
3. Existing replay reestablishes account restrictions, permanent keyed suppression, session/retry denial and durable personal-cleanup/billing tasks. It verifies matching key material; unresolved billing linkage is retained without granting product access. Acknowledgement covers only the exact replayed decision IDs, so a new confirmation during reconciliation prevents readiness.
4. Existing cleanup tasks remove known restored personal rows/owned resume objects and invalidate/remove export artifacts. Leases/fences/absence verification remain authoritative. Restored export authorization is denied for restricted subjects even if old bytes existed. Delivered bytes cannot be recalled. Fake Storage 403/unavailability/uncertain outcomes are not treated as absence; prior accepted export/cleanup checks remain applicable.
5. Required personal-cleanup jobs must be verified, and restricted export jobs must be invalidated, before readiness is released. **Protected legacy payload blockers keep the whole restored environment quarantined.** This stage does not redefine `primary_verified`, weaken ledger guards or claim a partial purge complete merely to reopen unaffected accounts.
6. Durable acknowledgement is followed by a process-local verified boot state. Restart starts closed even if a copied DB/checkpoint claims ready. Each request rechecks the current witness, generation/snapshot, complete outbox coverage and DB checkpoint; late/unpublished decisions, rollback or unavailable evidence closes access again. WebSockets are rejected with retry-later closure; HTTP exposes only `503 {status: restore_quarantined}`.

`C15_RESTORE_BOOT_REQUIRED=true` without operator composition yields quarantined HTTP and starts no workers/gRPC. Completing reconciliation after that startup does not secretly start omitted services: restart with a verified coordinator is required. There is no public restore endpoint, permission grant or customer-controlled checkbox. Normal customer/admin authorization still applies after readiness.

## Deployment integration still required

No existing operator restore identity/control plane exists in this checkout. The enforceable local contract is implemented, but production requires:

- Independently issued environment/dataset/restore-generation and **actual DB + object snapshot manifest** identities; verify those inputs against the snapshots being mounted. IDs in an authenticated record do not by themselves attest file contents.
- An external witness/key store and current-head lookup excluded from all DB/object/VM restore sets; protected read/write principals, atomic CAS/acknowledgement, outage/rollback/key-recovery testing. Keys are not loaded from operational dotenv in this rehearsal.
- A mandatory deployment boot composition selecting restore-required mode from that trusted control plane. This must not depend on a flag restored from the old database or an optional human checkbox. It must inject the coordinator before application startup and deny bypass through a normal boot profile.
- Fence **all** old source writers/decision acceptance before the source-seal lock is released, and prove all accepted decisions reached the independent journal. An asynchronous outbox cannot recover an accepted decision lost with its source DB **before publication**. Production needs a verified acceptance/publication and cutover protocol; local source sealing is not a promise against that unclosed window.
- Keep direct Auth/REST/Storage/CDN paths, workers, gRPC and callbacks behind deployment quarantine until the external acknowledgement. The local app middleware gates HTTP/WebSocket and startup suppresses workers/gRPC; it cannot close a separately hosted Supabase endpoint. During isolated replay, the existing gate enables maintenance DB work before external readiness, so **network/role isolation of the maintenance dataset is mandatory**. Do not expose direct DB/Storage based on its internal ready flag.
- Resolve legacy protected-payload cleanup before expecting affected restores to open. Retain suppression/replay/journal/checkpoint evidence over every restorable copy/callback horizon; no expiry deadline is invented. Actual backup-copy lifecycle, Auth, Storage and processor acceptance remain separate.

These are concrete activation blockers, not checks relabeled passed by native or fake-provider tests. Production export/deletion remains disabled.
