## Demonstrated defects and local fixes

1. **ZIP MIME mismatch.** The existing private exports bucket allowed several document formats but omitted `application/zip`. The actual Storage API rejected archive upload; the fake Storage adapter could not reveal that configuration mismatch. Candidate `supabase/migrations/20261101010000_privacy_export_storage_contract.sql` adds ZIP only to the existing **private exports** bucket, preserving other MIME types, privacy and limits. Resume MIME/write controls are unchanged.
2. **Direct Storage bypass of export expiry.** The actual pre-fix probe returned **200 for ready direct GET, 200 for direct signing, and 200 for direct GET after archive expiry before cleanup**. [Before-fix evidence](evidence/c15-actual-engines-20261101/expiry-before-fix/direct-archive-boundary.json). The same additive candidate adds a fixed, current-subject-bound restrictive Storage policy for durable C15 export-job namespaces. Customers cannot read/write/delete/sign those archive objects directly, even while ready; they must use the application's restriction/expiry/capability-checked download. The backend retains its private Storage path. The rule keys off durable job identity rather than a removable object manifest, so a late put cannot become an unregistered legacy export and reopen access. [After-fix evidence](evidence/c15-actual-engines-20261101/acceptance-final/direct-archive-boundary.json) records **400/400/400** with application ZIP delivery still successful.

No existing approved migration, immutable guard, historic ledger byte, FK, runtime auth assertion or role grant was weakened. The new SQL is a prepared additive candidate applied **only** in disposable databases. It does not activate normal export/deletion. Its fixed SECURITY DEFINER helper has `search_path=pg_catalog`, returns only an own-subject access predicate, grants no generic SQL or payload read and does not replace ownership RLS. Ordinary unrelated exports preserve their original ownership controls. Durable job/deny evidence must not be retired while an archive/late-write/restore source can still exist; no guessed metadata expiry is introduced.

Rehearsal defects were also fixed: internal-network host connectivity assumption; plain-Postgres Auth bootstrap ownership/search_path; missing standard authenticated default group; initial client MIME/connection-cursor/result-type expectations; and correct worker connection-factory injection. These are clearly separate from the two real export defects. Assertions were preserved and corrected to the documented API contracts, including `otp_limited` being a safe 200 state, rather than weakening a protected operation.

## Scope of acceptance and remaining blockers

- **Established here:** actual GoTrue 2.197.0 password/TOTP/custom hooks/SMTP/refresh revocation behavior for the tested synthetic flows; actual Storage 1.81.0 private HTTP/RLS/file handling; actual PostgREST checks; application router/worker integration with those engines. Earlier synthetic issuer results are not relabelled as these results.
- **Still unsupported/unverified:** real Google OAuth signup/linking/reauthentication, hosted Auth configuration and all mutation transaction/race paths; privileged import identity-level suppression (observed gap); full browser website+real-engine/real SDK navigation acceptance and complete production main/gRPC boot. Existing 23 intercepted browser and device checks remain useful historical evidence for unchanged UI, not engine-backed browser acceptance.
- **Revocation uncertainty:** later unauthorized response cannot prove an earlier global operation's completion; expired/missing authority remains blocked. Product denial and truthful pending/blocked status continue, but a supported reconciliation/recovery authority must be reviewed before activation.
- **Configured deployment:** production host/region remains unselected. Mandatory direct Auth/REST/Storage/CDN/gRPC fencing, independent restore witness/publication, TLS/gateway/key/principal composition and provider/log/backup/financial acceptance remain outstanding. A local internal network or local PostgreSQL is not production-independent durability. Existing signed capabilities have measured limits; already delivered files cannot be recalled.
- **Erasure/retention:** legacy immutable payloads and exact controlled-retirement authorization remain separate. The new SQL does not retire history or extend 90/180-day clocks to financial/suppression/restore evidence. Actual processor and backup-copy lifecycle is not established by destroying disposable test volumes.

Production activation stays disabled. No unsupported managed-Auth mutation trigger is added to conceal the privileged-creation gap. Before release, constrain privileged provisioning/import paths with a reviewed supported control plane and validate configured public/Google/link/email-change paths. Do not drop an acceptance gate merely because the runtime now works.
