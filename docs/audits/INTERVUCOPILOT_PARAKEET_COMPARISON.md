## A. Assessment

- **Stronger in demonstrated policy code:** Intervucopilot has explicit question extraction/classification, follow-up resolution, selected-resume authority, owned cloud session/JD checks, and gRPC guards against duplicate generation after an ambiguous stop. Parakeet's inspected client auto-triggers on natural share utterance boundaries; its hidden classifier/context algorithms are UNKNOWN. This comparison is about visible implementation, not proven accuracy or security superiority over its backend.
- **Equivalent capabilities, uneven coverage:** both have live ASR, partial/final state, forced endpointing, streamed answer display, cancellation, source labels, and timing hooks. Our implementation spans several transports, and some protections are stronger in gRPC than in the established WebSocket path. Parakeet exposes a more explicit shared transcription lifecycle and upstream flush contract.
- **Weaker/missing in the inspected paths:** our browser microphone uses `ScriptProcessor`, lacks an explicit buffered-audio flush barrier and `bufferedAmount` policy, and does not offer simultaneous microphone/system recording or reference-fed AEC. Our durable “transcript” is generated Q&A, not the complete recognized conversation. Device-change and acknowledgment liveness coverage is limited in the inspected browser streaming path.
- **Insufficient evidence:** comparative recognition quality, microphone/system alignment, speaker attribution accuracy, latency percentiles, CPU/energy cost, provider cost, real recovery success, and Parakeet's deployed models. Do not conclude its Speechmatics/native stack is faster or more accurate.

## 1. Current audio-to-answer pipeline

### Established microphone/manual path

`App.jsx` manual recording → `getUserMedia` → `createManualLiveSession` with a MediaRecorder backup. Browser microphone constraints are generally `audio:true`; gRPC-eligible capture requests mono/16 kHz. These are requests, not measured hardware settings. MediaRecorder uses supported WebM/Opus or other available MIME choices, not a guaranteed codec across platforms.

With manual-live configuration enabled, U2 converts Web Audio channel zero to PCM16 at 16 kHz and sends binary data to `/ws/auto-stt`. U8 bridges it to AssemblyAI. `Turn` messages return transcript, turn order, final flag and formatting information. U3 replaces interim text and records finals by turn order. Stop pauses capture, stops the backup recorder, requests `force_endpoint`, waits bounded finalization, then uses final-plus-preview text; failure/empty live text uses the recorded blob through `/transcribe/`. There is no explicit U2 “flush all outstanding captured frames” operation. Detection U12 then feeds `classifyAndGenerate` → context assembly/generation U13 → typed answer events/display U14.

Declared defaults in U16: manual batch provider `groq`, manual live provider `none`, Auto provider `assemblyai_streaming`, Auto fallback `whisper_local`. Therefore live manual capability is implemented but not enabled by the source default. Actual launch settings are UNKNOWN here. Batch STT can select OpenAI Whisper, Groq, AssemblyAI or local Whisper through U11; supported fallbacks are code paths, not evidence that all providers are configured or exercised.

### Established Auto microphone/system paths

Microphone Auto: U1 `startAutoStreamingMic` → U2 PCM → U8 WebSocket bridge → replaceable partial/final UI state → recent transcript assembly → `detectAutoQuestion` → generation. Client gates include run IDs, one Auto generation in flight, pending/latest question handling, a four-second cooldown, and recent-transcript duplicate suppression (60-second window). Error/close activates batch fallback, not seamless replay of the disconnected interval. Batch fallback segments are nominally four seconds for microphone and three seconds for system audio; segment duration is not ASR latency.

System Auto: U1 `startAutoStreamingSystem` → `/ws/auto-stt/system` → Python U7 WASAPI loopback → mono downmix/resampling/gain → AssemblyAI bridge → source-tagged transcript events → detection/generation. This captures the backend host's output device. It is not browser-tab capture on a remote website. U8 requests 80 ms native-rate reads; exported audio is target-rate PCM16. Silence is currently forwarded (`dropped_silence=False`), with RMS/peak/clipping diagnostics. This is not a local speech VAD.

Manual system audio uses backend start/stop recording endpoints and a WAV path before batch transcription/detection. U1 explicitly blocks **both-source recording and both-source Auto**. Source labels exist; a source is not proof of an identified speaker. No reference-fed paired-source AEC or speaker diarization was found in these wired paths. Browser microphone AEC/noise suppression effective defaults were not measured.

### Opt-in Electron gRPC path

Renderer U4 → narrow preload IPC → Electron main U6 → bidirectional `InterviewRealtimeService.StreamInterview` → Python U9 → AssemblyAI → typed partial/final/question/answer/status events → main snapshots/events → renderer/overlay. Audio is mono, 16 kHz, explicit PCM16 little-endian, framed at 3200 bytes = 100 ms. A final remainder is zero-padded and the ordered send tail drains before manual stop. Main permits one acknowledged audio chunk in flight; server bounds event/question/system queues at 32/4/3. System gRPC capture drops oldest queued frames and counts drops.

That acknowledgment is the backend's `audio_chunk_received` transport status, not proof of a recognition-service audio acknowledgment or final transcript. Distinguish capture, transport forwarding and recognition progress in any health policy.

`GRPC_REALTIME_ENABLED`, `GRPC_STT_ENABLED`, `GRPC_ANSWER_STREAM_ENABLED`, and manual/Auto/cloud pipeline flags default false. Manual gRPC rejects selected cloud/interview context and preserves the established authorized path. Cloud Auto U10 is implemented and validates current user, active owned session and selected resume/JD before loading generation context. Backend system gRPC exists, but U5's current renderer eligibility explicitly blocks system/both and only constructs microphone sessions: **partial integration, not a missing backend and not a default deployed feature**. Comments describing older G5 limitations are not reliable capability summaries.

Manual gRPC stop sends ForceEndpoint, waits up to 700 ms for a final, sends Terminate and waits a further bounded receiver drain. Generation is committed once. An ambiguous failure after stop does **not** rerun REST generation. Auto errors stop and ask for a restart instead of silently repeating a potentially committed turn. Preserve this safety property.

## C. Five most useful improvements

### 1. Reliable microphone framing and accountable backpressure — R1

**Current/equivalent:** U2 has a simple transport/capture split and PCM conversion; U4/U6 already order gRPC sends and bound in-flight work, U9 counts system drops. Don't replace those protections. U2's active gate can skip callbacks and has no socket backlog accounting. Its downsampler starts block-local; input-rate/frame continuity is not validated here.

**Parakeet evidence:** P1 confirms worklet framing; P2 confirms shipped bounded processing but warns that its 250 ms promise race can admit late out-of-order sends. Do not copy that race.

**Independent change/components:** put microphone framing on a worklet, carry source/session epoch, sequence/sample count and capture timestamp, preserve resampler state, and explicitly bound renderer→IPC→backend queues. Keep transport PCM16 unless a measured requirement warrants another format. A 4096-frame callback represents 256 ms at 16 kHz or about 85 ms at 48 kHz; these are analytical frame durations, not measured latency. Parakeet's 80 ms native holdback and 50 ms batching also add delay; “10 ms worklet” is not end-to-end latency.

**Benefit:** expected improved cadence and diagnosability under rendering load; magnitude UNKNOWN. **Cost/risk:** medium effort, worklet asset/build setup, sample-rate differences, resampling artifacts and queue policy; no ASR change or native dependency necessary initially. **Acceptance:** deterministic synthetic PCM at multiple negotiated rates, channel configurations and callback partitions produces the same sample count within documented rounding tolerance; no reordered sequence within an epoch; UI stress test reports queue age/depth and every drop, with no unbounded growth. Measure p50/p95 callback jitter and capture-to-send before/after.

### 2. Flush-before-answer contract and an ephemeral transcript ledger — R2

**Current/equivalent:** U3 already forces endpointing, bounds waiting and preserves a recording backup; U4 drains gRPC frames and pads its final tail. U15's durable Q&A is not a raw conversation transcript. **Evidence:** P2/P3 confirm upstream flush, finals accepted while stopping, separate completion/persistence flags and partial replacement.

**Independent change/components:** add `flush`/`drain` semantics to U2 and a source/epoch/turn ledger shared by manual/Auto adapters. Stop accepting new input, flush captured frames in order, request endpoint, await final or explicit timeout, then choose documented fallback. Never silently mark a partial as a final. Keep raw-final persistence a separate optional proposal, not a reinterpretation of existing Q&A/download/delete APIs.

**Benefit:** expected fewer trailing-word omissions and more trustworthy context provenance; unmeasured. **Cost/risk:** medium effort; bounded wait may delay answers; backup replay can duplicate speech if commit state is unclear. Durable raw persistence adds privacy/storage/schema/RLS costs and needs a decision. **Acceptance:** final frame <100 ms, delayed final, partial revisions, stop during IPC backlog, cancellation and missing final; recorded synthetic last words are either included once or reported incomplete. No answer is started twice; existing stored Q&A/deletion semantics remain intact.

### 3. One lifecycle/health policy, with explicit lost-audio recovery — R3

**Current/equivalent:** run IDs, epoch/version fences, disposal and safe fallback already exist in U1/U5/U6. U8 has socket ping settings, but transport ping does not establish audio acknowledgment progress. Device listing exists in U7; continuous browser device reacquisition is not established. **Evidence:** P4 confirms serialized actions, old-client identity fencing, acknowledgment watcher and budgeted capture recovery; it does not demonstrate seamless ASR replay.

**Independent change/components:** source-scoped state machine for start/record/flush/stop/recover, track-ended/device-change handlers, capture activity/send activity/provider progress diagnostics, bounded recovery and an explicit gap event. Validate the local bridge boundary before acquiring devices or opening paid provider sockets; do not assume HTTP CORS authenticates WebSockets. Retain server-held keys and main-held desktop credentials.

**Benefit:** expected fewer wedged sessions and more truthful recovery; unmeasured. **Cost/risk:** medium-high effort; retries consume recognition resources, reconnect can split turns, device permissions may require user action. No silent replay or generation retry after ambiguous commit. **Acceptance:** old close after new start cannot stop successor; switch/unplug device, suspend/resume, reject permission, stall provider progress and interrupt network; no leaked tracks/tasks, bounded resource count, visible lost interval and no duplicate paid generation. Security fixture rejects untrusted origin/session without opening a device/provider; legit configured local origins remain usable.

### 4. Consolidate trigger arbitration and live-answer idempotency — R4

**Current/equivalent:** our extraction/classifier, buffers, cooldowns, question fingerprints and safe post-stop behavior are already more explicit than the Parakeet client evidence. C9 has an independently implemented atomic idempotency pattern; reuse its principles, not its conversation semantics. `/generate` request IDs currently support tracing/storage, not demonstrated durable answer replay. **Evidence:** P5 confirms synchronous manual cooldown, cancellation and token-based supersession; no recovered server idempotency algorithm.

**Independent change/components:** share trigger arbitration between established and opt-in transports: manual priority, one session-generation slot, cancellation fence, duplicate normalized-question policy, and durable claim/attempt/replay only for a clearly defined live turn. Keep source/turn corrections distinct from new questions and preserve safe handling of ambiguous delivery. Evaluate stable partial/topic acceptance with a labeled corpus before changing it.

**Benefit:** expected fewer duplicate/missed turns and consistent manual/Auto overlap; unmeasured. **Cost/risk:** medium-high effort, server state/retention and failed-claim recovery; semantic dedupe can suppress a legitimate repeated question. **Acceptance:** simultaneous manual/final/cooldown events, repeated request IDs, reconnect after dispatch and crash after provider start yield one committed answer per authorized turn; a different user cannot claim/read another session's result. Statements, fragments, corrected partials, repeated real questions and code prompts retain intended detection behavior. Cancellation does not trigger an automatic paid retry.

### 5. Optional paired-source capture with tested echo handling — R5

**Current/equivalent:** separate microphone/system choices and honest “both not implemented” gates already work; U7 has loopback quality metrics. **Evidence:** P2 supports a render-reference AEC architecture, but effectiveness/compiled equivalence is INFERRED and latency impact UNKNOWN. Speaker/source differentiation in P3 is not proof of perfect speaker identity.

**Independent change/components:** only after confirming this workflow matters, align two independent source clocks/frames, feed playback reference into an independently selected AEC engine, retain separate transcription streams/source tags, and deduplicate echoes with provenance. Don't merge sources prematurely or disable browser AEC without a working reference path. Preserve the existing one-source default.

**Benefit:** enables a missing workflow and may reduce echo duplication; actual demand and quality gains UNKNOWN. **Cost/risk:** high effort, native ABI/signing/platform maintenance if native processing is chosen, ASR stream/resource multiplication, synchronization and double-talk distortion, possible holdback latency. Library/license/build compatibility remains unverified; do not add Sonora merely because Parakeet ships it. **Acceptance:** consenting synthetic double-talk, headphones versus speakers, delayed/missing reference, device clock drift and reference starvation; quantify echo attenuation, near-end preservation, duplicate-question rate, ASR error rate, CPU and added delay. Require a useful measured win before default enablement.

Ranking: R1 high expected impact/medium effort/high gap confidence; R2 high/medium/high; R3 high/medium-high/high for the coverage gap; R4 medium-high/medium-high/medium because current guards already cover many races; R5 conditional high/high/medium-low pending demand and acoustic measurements. This is a qualitative engineering ranking, not measured impact. R6 context budgeting and R7 telemetry are supporting work rather than reasons for a broad rewrite.

## D. Approaches not to adopt

1. **Do not switch ASR/LLM vendors or copy model labels on this evidence.** Speechmatics reachability is confirmed; quality/cost superiority and Parakeet's deployed LLM are unknown. Provider prices/docs and our actual configured deployment remain unverified.
2. **Do not treat every EOU as a question.** Keep our detector and test it. Parakeet's UI question-detection language does not expose its backend algorithm.
3. **Do not copy native holdback/queue constants or the timed-out IPC promise race.** Eight-frame delay/20-frame cap suit an unmeasured target; late async work must be fenced, not allowed to reorder.
4. **Do not replace WASAPI with first-source Chromium loopback blindly.** Our device inventory is useful; OS mix versus tab source, permissions and Windows deployment differ. Prototype only if portability/device handling justifies it.
5. **Do not mark transcript persistence successful merely because an answer stream finished/aborted.** P5 describes that client contract, not verified durable server acknowledgment. Require explicit receipts.
6. **Do not copy direct browser credential placement or broaden IPC invocation.** Keep our credential boundary, trusted sender validation and narrow bridge. If a future direct ASR connection is proposed, short-lived scoped minting, lifetime, replay, redaction and origin policy must be independently designed and verified.
7. **Do not copy document selectors, model menus, meeting-process monitoring or promotional UI.** They are unrelated to the immediate reliability gaps and can add privacy/security/maintenance work. A worker detecting microphone users is not VAD or transcription.
8. **Do not claim dropped speech was recovered, or replace physical deletion with a UI cutoff.** Our permanent deletion and temporary Clear Chat have explicit different semantics. Adding raw ASR storage needs its own retention design.

## F. Decisions genuinely needed before implementation

1. Is simultaneous microphone/system capture required, and which source should drive Auto answers? Should microphone speech be context only, or also a trigger? Without this, R5 remains optional.
2. Should raw recognized conversation be saved at all? Specify consent, retention, speaker/source labels, privacy expectations, downloads/deletion and whether it is distinct from today's generated Q&A.
3. During a network interruption, prefer an explicit pause/restart or a bounded in-memory audio replay window? Replay needs deduplication, memory bounds and a clear answer-commit rule; no seamless-recovery claim is justified now.
4. On manual/Auto overlap, should manual cancel/supersede the current answer or queue behind it? What should users see for the canceled partial answer? Preserve current safety until policy is chosen.
5. What validation corpus and acceptance thresholds define acceptable lost words, duplicate answers, first-visible-answer latency and CPU usage on target Windows hardware? None was supplied or measured here.

These uncertainties do not block this audit. Provider availability/pricing, active flags, effective device format, actual performance, deployed migration state and Parakeet backend internals remain documented unknowns; they should be resolved only through separately authorized, sanitized measurements and official documentation where needed.
